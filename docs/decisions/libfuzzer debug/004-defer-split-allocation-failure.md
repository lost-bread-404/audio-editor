# 004: 暂不处理 split 路径的分配失败，分支覆盖率就停在 ~88%

日期：2026-08-14
相关 PR：待提交（分支 `worktree-fuzz-coverage`）

## 决策

两件事都**先不做**，明确记录为已知缺口：

1. 不修 `tr_split_one` / `tr_split` 里 7 处不检查返回值的分配。
2. 不给 fuzz harness 加分配失败注入。

因此 `src/` 的分支覆盖率停在 88%，剩下的 12% 全部是分配失败路径、I/O 失败路径
（`fseek` / `fclose` 失败），以及内部调用者永远走不到的防御性判断。

## 理由

**缺口是真的。** `tr_split_one` 里 5 处、`tr_split` 里 2 处 `calloc`/`realloc` 之后
直接解引用，中间没有 NULL 检查：

```c
struct sound_seg *new_node = calloc(1, sizeof(struct sound_seg));
new_node->len = length;          // calloc 失败就是空指针解引用
```

而且两个函数都返回 `void`，**结构上就没有报告失败的能力**；调用方
`ss_track_delete` / `ss_track_insert` 也没有检查的余地。

**但草率地修会更糟。** `tr_split` 是边遍历边改图的：它对一个节点做完 split，再顺着
context 里所有 track 找出引用它的节点，逐个跟着 split，用一个工作队列驱动。中途分配
失败时，链表已经被改了一半——一部分节点分裂了，一部分没有，长度字段和 parent 指针
处于不一致状态。这时候：

- 直接 `return` 会把这个半分裂的结构留给调用方，后续任何读写都读到错的样本边界。
  这比当场崩溃更难查。
- 想回滚就要记录已经做过的每一次 split 并逆向撤销，等于再写一套镜像逻辑。
- 想"先把要用的内存全部预分配好再动结构"也不行：要 split 多少个节点取决于遍历过程中
  发现了多少引用者，事先不知道数量。

也就是说，正确的修法是重新设计 split 的失败语义，不是加几个 if。在没有想清楚回滚
方案之前动手，引入的 bug 会比修掉的严重。

**现实约束**：这条路径只有在 malloc 失败时才会走到。当前目标平台是桌面/服务器，
malloc 失败前系统通常已经不可用了。优先级低于已经修掉的 5 个输入可达的 bug。

## 放弃的方案

- **加 NULL 检查后直接 return**：见上，留下半分裂结构，是用一个更隐蔽的 bug 换一个
  明显的 crash。
- **给 harness 加分配失败注入**：能覆盖这些分支、也能证明 crash 真实存在，但在库还
  没有能力正确处理失败的前提下，注入器只会稳定地复现同一个已知问题，产出一堆指向
  同一根因的 crash 文件，噪声大于信息。应该等库先具备失败语义。
- **把覆盖率目标从"全分支"降到"全可达分支"并宣布达成**：本质上是改口径。这里选择
  照实记录 88% 和缺口成因。

## 什么情况下要推翻

- 库要用在 malloc 失败是正常预期的环境（嵌入式、设了硬性内存上限的容器），那时
  分配失败就是必须正确处理的常规路径。
- 想清楚了 split 的回滚/失败语义（比如改成"先构造完整的新链表，成功后再原子替换"），
  那时 1 和 2 应该一起做。
- 覆盖率被当成硬性门禁指标。那种情况下需要先把不可达分支和未处理分支在统计口径上
  分开，否则这 12% 会一直挂在那里。
