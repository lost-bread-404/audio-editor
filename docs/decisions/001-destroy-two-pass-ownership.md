# 001: 销毁 track 时分两趟移交样本所有权

日期：2026-08-14
相关 PR：待提交（分支 `worktree-fuzz-coverage`）

## 决策

`ss_track_destroy` 在释放节点之前，对本 track 的节点跑两趟 `tr_transfer_ownership`，
顺序固定：

1. 先跑**别名节点**（`has_data == 0`）：把所有指向它们的外部节点，改指到真正持有
   样本的那个节点上。
2. 再跑**持有数据的节点**（`has_data == 1`）：在仍然存活的引用者里挑一个，把样本
   缓冲区交给它。

另外两条配套约束：

- 移交开始前先 `tr_registry_remove`，让扫描只看得到会活下来的 track。
- 别名解析要一路爬到真正持有数据的节点，不能只跳一层。

## 理由

三个 use-after-free 都是同一个根因的不同侧面：一个节点被释放了，而别的 track 还指着
它。fuzz 里 `ss_track_insert` 把一个 track 的片段插回它自己，会在**单个 track 内部**
造出别名，这让"引用者一定在别的 track 里"这个隐含假设不成立。

顺序是这个设计的全部要点：

- 第 1 趟把所有外部引用**收拢到持有数据的节点上**，第 2 趟才看得见它们、才能把缓冲区
  交出去。
- 反过来先跑第 2 趟，第 1 趟随后又会把引用改指到马上要被释放的节点上。

"持有数据"和"会活下来"是两个不同的性质，代码里只检查前者就会出事：爬链可以正确地
停在一个确实持有数据的节点上，而那个节点恰好属于正在销毁的 track，销毁流程后面会
无条件释放它。先摘掉注册表只解决了扫描端，爬链是直接顺着指针走的，绕过了注册表。

约束条件：节点固定 24 字节（`sound_seg_extra.h` 明确写了 do not add fields），所以
不能靠给节点加字段来解决。

## 放弃的方案

- **给样本缓冲区加引用计数**：最直接，但要在节点里加计数字段，突破 24 字节上限。
  这个上限是库的公开卖点（README 首段），不能为了内部实现方便就破坏。
- **销毁时把数据复制给引用者**：语义上最简单，但库存在的意义就是"分割/重排只动指针
  不拷样本"，销毁路径上引入 O(n) 拷贝等于把这个保证打穿。
- **单趟移交**（原实现）：无法成立。一趟扫描里，改指的目标可能是还没处理、也可能是
  已经处理过的节点，两种情况都会留下悬垂指针。

## 什么情况下要推翻

- 节点大小上限放开（比如版本升到 1.0 允许改布局），那时引用计数是更简单、更难写错的
  方案，应该换过去。
- 库要支持多线程共享 track。现在的移交逻辑假设销毁期间没有并发读者，加锁或改成
  原子引用计数都会让这套顺序假设失效。
- 如果 `tr_split` / `ss_track_insert` 改成不再产生 track 内部自别名，第 1 趟的必要性
  需要重新评估。
